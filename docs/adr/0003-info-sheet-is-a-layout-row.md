# 說明卡是版面裡的一格，不是浮在圖上的一層

說明卡（bottom sheet）升起來時，平面圖被**擠進卡片上方那條可視帶**並等比縮小，
而不是被卡片蓋住下半部。頁面因此改成一個 `100dvh` 的 flex column，
只有平面圖那一格會被壓縮（`app/layouts/[id]/page.module.css`、
`components/FloorPlanViewer.module.css` 的 `.viewport`）。

## 為什麼

`viewBox` 是 `1197 × 1256`，比寬還高：375px 的手機扣掉頁面 padding，圖畫出來約 360px 高。
卡片一升起來將近 400px，圖的下半（次臥、後陽台、主臥衛浴那一帶）就被壓在卡片底下。
PRD §6.1 要的是「看說明的同時還看得到那個符號在圖上的位置」——在那半張圖上，浮層版本不成立。

**做法是重新 fit，不是平移。** `zoom 1` 的定義就是「整張圖剛好放得下」，
單純把視野往上推會被 `clampView` 擋住、上方露出空白。改成以可視帶的高度等比縮小，
整張圖連同選中標示都留在看得到的地方。

## 代價：換算層多收一個可視帶高度

`lib/viewer/view.ts` 原本寫著一條規則：

> 可視區域的高度由寬度與 viewBox 的長寬比推出來，不另外量。
> 量兩次會得到兩個互相矛盾的數字，而「zoom 1 剛好放得下整張圖」這件事就不再成立。

**這條規則被這個決定推翻了**，所以在這裡留下紀錄。它背後的顧慮仍然成立，只是換了守法：

- 可視帶高度**不是第二次量測**。它由版面決定（卡片佔掉多少，剩下的就是可視帶），
  並且與寬度一起從**同一個 `ResizeObserver` entry** 讀出來。高度只有一個來源，
  沒有「兩個互相矛盾的數字」的空間。
- `zoom 1` 的意思收窄成「**寬度**剛好放得下」，框比圖矮時 `fitZoom` 小於 1。
  `clampView` 因此補上一個分支：可視範圍比圖大時置中而不是貼邊——
  少了它，圖會在卡片升起的瞬間往左上角偏過去。

同時被推翻的還有一條隱含假設：**版面高度變化不代表使用者的選擇作廢**。
`RESIZE` 因此分成兩條路——寬度變了（比例尺變了，候選作廢，退回第一段），
高度變了（卡片自己升起或收起，stage 不動，只按 fit 的變化比例調整縮放）。
少了這個分岔，卡片一開就會把自己關掉。

## 這個決定改了誰的東西

- `lib/viewer/view.ts`：`Projection` 多一個 `viewportHeight`；新增 `fitZoom`；
  `fitView` 改成吃整個框；`clampView` 補置中分支。
- `lib/viewer/interaction.ts`：`ViewerState` 多一個 `viewportHeight`；`RESIZE` 分兩條路。
- `tests/two-stage-tap.spec.ts` 的「最壞情況」：卡片升起會讓圖上同一個位置換掉螢幕座標，
  迴圈外量一次的座標到第二圈就不成立，改成每圈關掉卡片、等圖長回全圖、重新量。

## 還沒付的帳（票 04 已付）

票 04 的 pan/zoom 落地後，使用者會有一個「自己調好的視野」。
現在卡片升起是按 fit 的變化比例調整縮放，等於**等比縮放使用者的視野**，
沒有把它丟掉——但那條路徑至今沒有真的被走過（M2 還沒有自由縮放）。
票 04 應該把它走一次，確認「開卡片 → 關卡片」回得到原本的視野。

**2026-09-08：走過了，而且路上有洞。** 等比調整本身是對的，但 `RESIZE` 夾視野時
用的是**舊框**配新倍率——算出來的可視範圍偏小，視野被往裡推一小段，而框變回來時
那一段不會自己還原。使用者放大到 2 倍、開一張說明卡再關掉，圖就偏掉 2.8px。
成因與這個決定同源：`Projection` 收了可視帶高度之後，「框」開始參與換算，
而拿舊框配新視野正是這一層一直以來壞掉的方式。
測試 `tests/pan-zoom.spec.ts`「使用者自己調好的視野撐得過說明卡的開與關」守住這條路徑。

**2026-09-13：`100dvh` 的那個 column 往外移了一層（M3 票 04）。** 免責頁尾進了根版面之後，
`100dvh` 的 flex column 是 `body`（`min-height`，`app/globals.css`），平面圖頁是它的第一列
（`flex: 1 1 0`），頁尾是最後一列。**這個決定本身沒變**：說明卡仍然是版面裡的一列，被壓縮的
仍然只有 `.viewport`。多出來的是兩件事：卡片升起時頁尾讓位（`components/SiteFooter.module.css`），
否則同一句免責會印兩次，而展開時的可視帶會從 74.8px 被壓成 17.5px（375×812）；以及矮螢幕
（高度約 581px 以下）上，第二段的「重選」列會讓框在兩下點擊之間變矮，走的是同一條 `RESIZE`
高度的路（`tests/site-footer.spec.ts` 在 375×568 釘住）。

**2026-09-14：找找看頁的卡片展開時，可視帶是 0（M4 票 02）。** 找找看頁比平面圖頁多兩列：題目，以及作答後「下一題」那一列。
375×812 下卡片開著時框剩 242.7px，**展開時是 0px**——「看說明的同時還看得到那個符號」在那一刻不成立，標記還在 DOM 裡但看不到。
暫時接受：展開是讀者自己要讀完整內容，收合時標記都看得到；怎麼擠出那一列是版面的取捨，交給 M4 票 08 重畫設計稿時定（數字與理由在票 02 的 Comments）。

同一次發現的洞：框被壓成 0 高時 `fitZoom` 算出 0，之後每一次等比調整都是拿 0 去乘，框長回來那一次又是除以 0，圖停在 `scale(0)` 回不來。
`RESIZE` 因此**不收 0 寬或 0 高的框**，留著上一個真的框（`lib/viewer/interaction.ts`）。矮螢幕上的平面圖頁卡片展開時也會走到這條路。

**2026-10-01：找找看的 0 高可視帶已解決（拼厝票 06／07）。** 結果區把判定、被點名字及正確答案明確列出後，
固定列佔用的高度會隨名字長度變動，單靠固定的 Sheet 上限不夠。`QuizRound` 從實際版面扣掉題目、結果、
下一題及間距，再保留圖面的最小高度，把剩餘額度交給 InfoSheet；說明卡仍然是版面裡的一列，正文自己捲動。
高度預算由找找看的 owner 計算，InfoSheet 不必知道關卡或答題狀態。
`tests/responsive-regressions.spec.ts` 與 `tests/pin-chhu-regressions.spec.ts` 守住答對／答錯、展開／收合及最長現有名稱，
320 × 568 仍保留至少 84px 圖面、48px 可捲正文，沒有 document scroll。上述 2026-09-14 的暫時接受因此結束；
`RESIZE` 忽略 0 尺寸的防護仍保留。
