# 06: 平面圖頁與首頁的找找看入口

**What to build:** 他在三房兩廳平面圖上點了一陣子，想測測自己，入口就在頁面上；第一次到首頁的人也看得到找找看的入口，可以直接從玩開始。從 Google 落在符號頁的人，看到的仍然只有那一顆「這個符號在真實格局裡長怎樣 →」。

**Blocked by:** 01（入口要有地方連）

**Status:** done

規格：`.scratch/m4-quiz/spec.md` 的「路由與頁面」；PRD §8。

## 注意

- **平面圖頁的入口不得讓檢視器的框變矮。** 那一頁是 100dvh 的版面，每一列都從平面圖的可視帶挖高度（ADR-0003）；平面圖頁的 `<h1>` 刻意不換成長標題就是同一個理由。擺在既有的列裡，不另起一列
- **首頁的入口與「開始探索」按鈕同樣由資料產生**，只替有可出題符號的 layout 產生，不寫死 `3b2l_standard`
- **符號頁不放**：它的轉換點是把搜尋流量帶進產品核心的唯一入口（PRD §6.2.1），不該被第二顆按鈕分散
- 文案進集中管理的文案模組

- [x] 首頁每張有可出題符號的 layout 各有一個入口，連到對應的找找看頁
- [x] 符號頁上沒有連往找找看頁的連結
- [x] 既有首頁與平面圖頁的測試維持綠

### 「框高度與加之前相同」怎麼驗

量到的數字（375 × 812），加入口之前的建置產物與之後逐 px 相同：

| 狀態 | 框的高度 |
|---|---|
| 說明卡沒開 | 359.9px |
| 說明卡開著 | 348.8px |
| 說明卡展開 | 74.8px |

測試裡的做法是**同一頁把入口藏起來再量一次**，三種狀態各比一次。
- 擋得住的：入口撐高了它所在的那一列。
- 擋不住的：包住入口的那一列本身就比原本單獨的 `<h1>` 高。這一半靠上面那張表對過。
- 票面只要求收合與升起兩種，多量了展開：展開時框只剩一條，最經不起多挖。

### 小決定

- **符號頁「沒有入口」掃建置產物裡的每一張符號頁**，不列舉符號：清單明天多一個符號時不會紅，只會少測一頁。

### 全套測試抓到的：Tab 的第一站變了

- **症狀**：`tests/keyboard.spec.ts` 三條紅。這張交出去時只跑了頁面層的測試，沒跑鍵盤那份。
- **原因**：入口排在標題列、在圖的上面，所以 Tab 的第一站從第一個熱區變成這個入口。
  那三條測試假設「按一次 Tab 就到第一個熱區」。
- **沒有改入口的位置**：spec 要它擺在既有的列裡，而標題列本來就在圖的上面。
  焦點順序跟著畫面由上而下是對的；把它在 DOM 裡搬到圖後面、再用 CSS 排回上面，焦點順序就與畫面對不上（WCAG 2.4.3）。
- **改的是測試**：先 Tab 過圖前面的東西，走到第一個熱區才開始記。
  測試原本要保護的東西都還在：每個熱區走一次、依房間與類別的順序、熱區之間不夾別的東西、焦點看得出來。

### 兩軸 review 之後改的

- **首頁找找看按鈕的樣式不再照抄 `primaryAction`**：原本抄了九行，卻漏了鍵盤焦點框。
  `reading.module.css` 拆出共用的 `actionShape`（大小、排版、焦點框）；`primaryAction` 在它上面填墨色底，找找看的按鈕在它上面描框線。
- **`homeQuizButton` 由 `LAYOUT_QUIZ_LINK` 組出來**，不再另寫一次同一句。
