# M3 符號頁、分類瀏覽與搜尋

Status: ready-for-agent

## Problem Statement

有人在 Google 打「平面圖 虛線 是什麼」。

他沒聽過這個網站，也不會先到首頁——他會直接落在某一頁上，而那一頁就是他對這個網站的全部印象。搜尋結果現在給他的是一堆內容農場文章：每一篇都講得很確定，沒有一篇說得出自己憑什麼。M1 的試查甚至撞到過一篇，搜尋摘要宣稱它說明了「樑以虛線表示」，實際打開全文沒有提到樑、也沒引用任何標準。

而這個網站對他來說目前**不存在**。它只有一個 `/layouts/3b2l_standard`，`/` 是 404，14 個符號沒有任何一個有自己的網址。就算他誤打誤撞找到了那張平面圖，他也走不完「我想知道虛線是什麼」到「圖上那條虛線在哪」這段路——圖上有 37 個熱區，沒有一個知道他要找的是樑。

更麻煩的是反方向：M2 蓋好的那個檢視器是這個產品最有價值的東西，但沒有任何一條路通到它。

## Solution

14 個各自獨立、可被搜尋引擎索引的符號頁，加 3 張分類頁，加一個首頁。

每一張符號頁自己站得住：標題直接對應搜尋意圖（「平面圖上的樑是什麼？」而不是「樑」），內容說得出這個答案從哪份文件的哪一頁來，容易跟什麼搞混、差在哪裡。頁面底部一個按鈕把他帶進平面圖，**並把這個符號在圖上的所有位置同時圈亮**——9 扇窗一起亮。

這個按鈕是把 SEO 流量帶進產品核心的唯一入口，它的重要性高於首頁設計（PRD §6.2.1）。

而「樑」沒有位置可以圈亮——建案平面圖多半不畫樑，這正是它要教的事。它的按鈕寫「這張三房兩廳上看不到樑——這正是重點 →」，落地時圖上跳一條橫幅說明。轉換率照樣量得到，而且這一頁的說服力更強。

## User Stories

1. As a 從 Google 進站的人, I want 搜尋結果點進來就是一頁完整可讀的內容, so that 我不必再從首頁往下找
2. As a 從 Google 進站的人, I want 頁面標題就長得像我剛才打的問題, so that 我在搜尋結果裡認得出這一條值得點
3. As a 首購族, I want 一句話就知道這個符號是什麼, so that 我三秒內有答案，不必讀完整頁
4. As a 首購族, I want 看到這個符號畫出來長什麼樣, so that 我能拿它去對照手上那張圖
5. As a 首購族, I want 頁面上的符號圖形跟平面圖上畫的是同一種畫法, so that 我在這裡認得的形狀，回到圖上找得到
6. As a 首購族, I want 知道這個說法出自哪份文件的哪一頁, so that 我可以自己判斷要不要信
7. As a 首購族, I want 看到來源徽章告訴我這是國家標準、法規、業界慣例還是畫法不一, so that 我知道這個答案硬到什麼程度
8. As a 首購族, I want 當這份標準是轉載來的時候頁面直說, so that 我不會以為他們真的翻過國家標準原文
9. As a 首購族, I want 法規類的來源可以點出去看全文, so that 我要查證的時候不必自己 Google 法條名稱
10. As a 首購族, I want 知道這個符號容易跟哪個搞混、差別在哪, so that 我下次在圖上不會認錯
11. As a 首購族, I want 知道這個符號在買房時該注意什麼, so that 我知道它跟我的錢有什麼關係
12. As a 首購族, I want 沒有注意事項的符號就不要留一個空欄位, so that 我不會以為頁面壞了
13. As a 首購族, I want 每一頁底部都有免責聲明, so that 我知道實際要以個案圖說為準
14. As a 首購族, I want 頁面底部有個按鈕帶我去看真實格局, so that 我不是只讀到一個抽象的圖例
15. As a 首購族, I want 按下去之後圖上這個符號的每一處都亮起來, so that 我知道它在真實的圖上長在哪些地方
16. As a 首購族, I want 高亮之後我還是能自由縮放與拖曳, so that 我可以自己湊近看某一處
17. As a 首購族, I want 高亮之後我隨時可以直接點圖上別的東西, so that 我不必先關掉什麼才能繼續探索
18. As a 首購族, I want 看樑的時候按鈕誠實告訴我圖上看不到它, so that 我不會進去之後找不到而以為網站壞了
19. As a 首購族, I want 進去之後有一條說明告訴我為什麼看不到樑, so that「看不到」這件事本身變成我學到的東西
20. As a 想查特定符號的人, I want 一個搜尋框, so that 我不必在三張分類頁裡翻
21. As a 想查特定符號的人, I want 打俗稱也找得到, so that 我打「灑水頭」不必知道正式名稱叫什麼
22. As a 想查特定符號的人, I want 大小寫、全形半形、前後多打的空白都不影響結果, so that 我不必為了搜尋而小心翼翼地打字
23. As a 想查特定符號的人, I want 搜尋當下就出結果不用等, so that 它用起來像個工具而不像個網頁
24. As a 想瀏覽的人, I want 依結構／門窗／家具家配三類瀏覽, so that 我可以一類一類看完
25. As a 想瀏覽的人, I want 分類頁不要出現空的分類, so that 我不會點進一個沒有東西的頁面
26. As a 第一次到首頁的人, I want 一句話說清楚這個網站在幹嘛, so that 我決定要不要往下走
27. As a 第一次到首頁的人, I want 一個明顯的按鈕直接進平面圖, so that 我不必自己找入口
28. As a 使用者, I want 網址列不再出現 404, so that 我把網址剪掉尾巴還是到得了地方
29. As a 鍵盤使用者, I want 用 Tab 走得完符號頁與分類頁上所有可操作的東西, so that 我不需要滑鼠也能用
30. As a 讀螢幕的使用者, I want 符號圖形有替代文字, so that 我知道那張圖畫的是什麼
31. As a 搜尋引擎, I want 每一頁有自己的標題與描述, so that 我不會把 15 個頁面當成同一頁
32. As a 搜尋引擎, I want 一份 sitemap, so that 我找得到全部的頁面
33. As a 搜尋引擎, I want 內容在 HTML 裡就有, so that 我不必執行 JavaScript 才讀得到
34. As a 內容維護者, I want 頁面上的字全部來自 symbol 資料, so that 我改一次資料，符號頁、分類頁、說明卡、搜尋一起改
35. As a 內容維護者, I want 分類頁的數量由資料算出來, so that 我加一類符號時不必回頭改程式
36. As a 內容維護者, I want 我補第 2 個交叉來源之後頁面自動多一行, so that 我不必為了排版回來改元件
37. As a 內容維護者, I want 符號頁的按鈕連去哪張圖由資料決定, so that 我日後加第 2 張格局圖時不必改程式
38. As a 開發者, I want 平面圖頁不要被迫載入符號頁才用得到的欄位, so that 我不會為了一個頁面的需求拖慢另一個頁面
39. As a 開發者, I want 資料驗證失敗時 build 直接中斷, so that 壞掉的資料進不了正式站
40. As a 開發者, I want 檢視器的兩段式點擊不因為多了高亮而變得更難懂, so that M4 接手時狀態機還是三個階段

## Implementation Decisions

### 路由

M3 交付四組路由，全部 SSG（`next.config.ts` 已經是 `output: "export"`）：

- `/` — 首頁。一句主張、一個「開始探索三房兩廳」的按鈕、搜尋框、三個分類入口。**不做**長篇敘事、示意圖、統計數字
- `/symbols/[id]` — 14 頁
- `/categories/[id]` — 3 頁
- sitemap

**不做 `/symbols` 索引頁**：它跟三張分類頁講同一件事，而 §6.2.1 明講符號頁不該是「首頁 → 分類 → 符號」導覽樹的末端，再加一層總覽是往反方向走。

**不做 `/search` 路由**：SSG 產不出搜尋結果頁的 HTML，那一頁對搜尋引擎是空殼，卻仍然會被收錄。

**任何地方不得寫死 `3b2l_standard`**。M2 已經守住這條（路由是 `[id]`），M3 的轉換點按鈕同樣要從資料取得目標。

### 資料投影：三個消費者，三種形狀

`lib/symbols/` 現有的 `loadSymbols()` **刻意只挑前台要的欄位**，因為它的回傳值會被當成 props 序列化進靜態 HTML。M3 需要的欄位比說明卡多（`aliases`、`source_refs`、`related_layouts`、`svg_ref`），但**不能直接加進去**——那會讓每一張平面圖頁都夾帶 14 筆查證資料出貨。

因此維持一個模組、三個投影，各自由「它要不要過網路」決定形狀：

| 消費者 | 需要 | 會不會序列化進 HTML |
|---|---|---|
| 檢視器說明卡（既有） | 現有欄位，不動 | 會（client 元件的 props） |
| 符號頁 / 分類頁（新） | 加 `svg_ref`、`aliases`、`source_refs`、`related_layouts` | **不會**——server component 直接渲染成 HTML |
| 搜尋索引（新） | 只要 `id`、`name`、`aliases`、`category` | 會，但極小 |

`verification_status`、`ai_description`、`detection_hints`、`_pilot_note` **三個投影都不含**。前兩者是階段二預留（PRD §7.2.1），後兩者是內部備註；`verification_status` 不上前台是 M2 已定的規則（`CONTEXT.md`）。

### 符號頁

欄位順序（與說明卡刻意不同——說明卡是站著看的，符號頁是搜尋落地頁）：

1. 標題：對應搜尋意圖，由 symbol 資料生成，不是把 `name` 直接當標題
2. 大尺寸來源徽章（PRD §7.2.2）
3. 符號圖形，取自 `data/symbols.sprite.svg` 的 `svg_ref`
4. 白話意思
5. 容易搞混——**排在注意事項之前**。`confused_with` 是這批內容裡最貼近搜尋意圖的東西（「柱跟牆怎麼分」正是人們會打的字），埋在下面浪費它
6. 注意事項——`caution` 為 `null` 時整區不出現，不留標題也不留空白（14 筆裡只有雨遮有）
7. 完整出處：每筆 `source_refs` 一行，印 `doc` + `clause` + `year`；`cns` 的 `via` 整行印出
8. 轉換點按鈕

**出處的連結規則**：**有 `url` 就渲染成連結，沒有就印純文字**，不因為缺連結而少印一筆來源。

公會規範**永遠不連、也不 host PDF**——那是別人的著作，repo 根目錄那份 `平面圖符號.pdf` 不進 `public/`。會有 `url` 的只有 `regulation` 類（全國法規資料庫全文免費公開）。

**現況是 15 筆 `source_refs` 沒有任何一筆有 `url`**，所以 M3 剛落地時全部會是純文字。缺的那兩筆（雨遮的地籍測量實施規則、建築技術規則）屬於 M1，已另外開票。**這不構成對 M1 的依賴**：渲染端對 `url` 缺席是安全的，M1 補上之後連結自己長出來，不必回頭改元件。連結那條路的測試用 fixture 驗，不等真資料。

`source_refs` 的 `clause` 是**定位資訊**（頁碼、表號，加一句足以辨認的短引），不是內容轉錄。PRD §7.1 的著作權紀律在符號頁上仍然有效：說明文字一律自行白話重寫，符號 SVG 一律自行重繪。

### 分類頁

分類清單**由資料算出**：掃過所有 symbol 的 `category`，出現過的才產生頁面。現在是 3 頁。

不為 `SymbolCategory` 以外的 enum 值產生空頁面（Google 會當 thin content），也不另外手寫一份「就這 3 類」的常數——那會變成第二份會跟資料分岔的名單，正是 PRD §9「不得各自維護副本」要防的事。中文名沿用 `lib/ui/copy.ts` 的 `CATEGORY_LABELS`。

### 搜尋

client 元件，索引在 build 時內嵌進頁面（14 筆 × `id`/`name`/`aliases`/`category`，約 2KB），**不 fetch、不打 API**。放首頁與三張分類頁。

比對規則：`name` 與 `aliases` 都比，子字串命中即可。正規化只做三件事——**大小寫、前後空白、全形轉半形**。

**不做簡繁轉換**：受眾是台灣人（PRD §3），加一張對照表要維護，而且會讓比對結果變得難以預測。

比對邏輯放 `lib/symbols/`，與 UI 分開。M4 的找找看要從同一份索引出題，分開才不必重寫。

### 轉換點與高亮

**URL**：`/layouts/<layout-id>?symbol=<symbol-id>`。目標 layout 取自該 symbol 的 `related_layouts`。

不用新路由：那會產生 14 個內容幾乎相同的可索引網址，自己製造重複內容。

**不用 hash 的理由不是「hash 會閃」**——`output: "export"` 之下沒有伺服器看得到 query，`?symbol=` 一樣只能在 hydration 之後讀到，兩者在這件事上打平。選 query 是因為它是框架支援的那條路（`useSearchParams`）、是規範的可分享網址形式，而且爬蟲看得到它是同一頁的參數而不是另一個片段。

**實作注意**：`output: "export"` 之下，`useSearchParams()` 必須包在 Suspense 邊界裡，否則 build 會直接失敗。這是這個決定唯一的實作成本，先知道就不會在票裡撞牆。

**狀態機**：新增一個 action，語意是「把這個 symbol 的所有熱區標成 `highlighted`」。

- **stage 維持 `browsing`**，不新增第四個階段。高亮期間使用者本來就該能自由 pan/zoom、也該能直接開始新的第一段點擊，而那正是 `browsing` 的行為
- **開始選東西的那一下清掉高亮**：圈出候選的 `TAP`、第二段的確認、鍵盤 Enter。**點到空白處（沒有圈出任何候選）不清**——雙擊的第一下就是這種，清掉的話雙擊放大之後圖上什麼都不亮，與 user story 16 相反。高亮是疊在 `browsing` 上的一層，不是一個階段（2026-09-13 決議 D1，票 08；原本寫「任何 `TAP` 清掉高亮」）
- **視野維持 fit**，不自動放大。9 扇窗散在全圖，放大只會藏起其中幾處
- **狀態列說出處數**：落地時說「窗在這張圖上共 9 處，都亮起來了。」，第一次進站的人後面再接那句引導（票 05）。對到 0 處時不說這一句，由樑的橫幅接手（2026-09-13 決議 D2）
- **`?symbol=` 對不到任何符號**（網址打錯或不完整）：不高亮，狀態列提示找不到網址指定的符號。**不把網址裡的字印出來**——網址是別人造得出來的，照印等於讓第三方在頁面上寫字。狀態機因此只收真的符號，樑的橫幅可以直接以「對到 0 處」為條件（2026-09-13 決議 D4）

**不得把這些熱區塞進 `candidates`**。`candidate` 的語意是「第一段容錯圈出的候選」，而使用者從符號頁進來時根本沒有點過。

**理由是視覺與詞彙，不是命中判定。** 命中那條路其實不會壞：`tap()` 是看 `stage` 分流的（`stage === "candidates"` 才走 `confirmTap`），stage 既然維持 `browsing`，第二段的 30px 判定永遠不會接管，下一次 `TAP` 會直接用容錯半徑重算候選集並覆蓋掉。

真正會壞的是**畫面與語意**：檢視器的 `data-state` 只看「在不在候選集裡」，不看 stage，所以塞進去的熱區會被畫成 `candidate`——與真正的第一段候選視覺上完全無法分辨，而使用者其實沒有點過任何東西。`CONTEXT.md` 已經把 `highlighted` 與 `candidate` / `selected` 分開登錄並明講不可互相概括，這條決議是在兌現它。

**鍵盤路徑**：`SELECT_HOTSPOT`（Enter）與 `TAP` 一樣清掉高亮——它同樣是「使用者自己選定了一個熱區」，走的也是同一個 `confirmSelection`。`FOCUS_HOTSPOT`（Tab 移動焦點）**不清**：那只是焦點在走，使用者還沒選定任何東西，把高亮撕掉會讓他失去剛剛帶進來的脈絡。

**樑（0 個匹配熱區）**：走**同一個 URL、同一個 action**，特例只落在呈現上——圖面跳一條橫幅說明「建案平面圖通常不畫樑，它在施工圖與結構圖上」。

不開說明卡：使用者剛在符號頁讀完同樣的內容，再推一次是重複；而且說明卡在 M2 是綁著「選中了某個熱區」才開的，沒有熱區硬要開卡會弄髒那條規則。

### 全站

- **免責聲明進根版面的頁尾**（PRD §6.4「每頁固定顯示」）。`lib/ui/copy.ts` 的 `DISCLAIMER` 已經存在、註解也已經這樣寫，但目前只有說明卡在用
- **說明卡裡那一份保留**：卡片升起來時會蓋住頁尾，兩份服務的是不同時刻的同一個人
- **每頁自己的標題與描述**。目前 `/layouts/3b2l_standard` 用的是根版面的「平面圖教學」，跟首頁同名——M3 一併修掉
- **不做 JSON-LD 結構化資料**：PRD 沒要求，多一層要跟著資料維護的東西

### 建置時驗證（`validate_data.py` 加三條、改一條）

沿用既有風格：錯誤訊息要說明**為什麼**這條規則存在，不只說哪裡錯。

1. 每個 symbol 的必填內容欄位非空（`name`、`plain_meaning`、`svg_ref`、`category`、`source_tier`、`related_layouts`）。`related_layouts` 是 2026-09-13 補的（決議 D3）：空陣列不會讓任何東西報錯，只會讓那一頁安靜地沒有轉換點按鈕
2. `related_layouts` 裡的每個 id 都對得到實際存在的 layout
3. 每個 symbol 的 `category` 必須落在**階段一的三類**（`structure` / `door_window` / `furniture`）。`validate_data.py` 現在的 `VALID_CATEGORIES` 還留著 v0.4 砍掉的 `plumbing_electric` 與 `fire_safety`，要收窄；錯誤訊息要說明設備類是 v0.4 砍出範圍的，不是打錯字

   **這一條刻意不寫成「每個 category 都有中文名」。** 中文名在 `lib/ui/copy.ts` 的 `CATEGORY_LABELS`，那是 TypeScript，掛在 prebuild 的 Python 驗證器讀不到它——寫成那樣就得在 Python 裡再抄一份中文名，變成第二份會分岔的清單。改成兩半各自用看得到事實的語言把關：**Python 管「資料裡的分類合不合法」，TypeScript 管「合法的分類有沒有中文名」**（`CATEGORY_LABELS` 型別是 `Record<SymbolCategory, …>`，少一個 key 直接編譯失敗）。合起來的保證與原本那條相同，而**中文名只有一份**。兩半之間仍有一份手工同步的東西：合法分類的 id 清單本身（Python 的 `VALID_CATEGORIES` 與 TypeScript 的 `SymbolCategory`），由 `tests/build-validation.spec.ts` 比對，分岔時說得出是哪兩份。

**「符號在不在那張圖上」維持 warning**，不升為 error。樑就是那個預期中的例外（PRD §10.1 明講不可以寫成 error，否則會逼未來的維護者為了消錯而畫一根不存在的樑）。

#### 要改的那一條：`caution` 必須從 `REQUIRED_WHEN_VERIFIED` 移除

**這一條是 M3 與 M1 之間唯一會讓兩線並行斷掉的耦合點。必須在 M3 最早的票裡處理，不能排到後面。**

（另一個接觸面是 `source_refs` 的 `url`，但那不是耦合——見「符號頁」的連結規則：沒有 `url` 就印純文字，M1 補上之後連結自己長出來，兩邊誰先誰後都不會弄壞對方。）

`REQUIRED_WHEN_VERIFIED` 目前是 `[plain_meaning, caution, source_refs, verified_at, verified_by]`，而 14 筆裡**只有雨遮有 `caution`**，其餘 13 筆是 `null`。後果：

- M1 一把任何符號翻成 `verified`，資料驗證就失敗 → `prebuild` 失敗 → build 斷掉 → M3 全部的頁面測試一起掛（`webServer` 跑的是 `npm run build && npm run start`）
- 在這條規則下，**只有雨遮可能是 `verified`**，查證率上限 1/14 = 7%。M1 的 80% 門檻仍然是算術上不可能——2026-09-12 的 Q6 只拆掉了兩道閘門裡的第一道

**`caution` 不該綁進查證完備性**。`verification_status` 描述的是「來源查證做到哪」，而 `caution`（買房時要注意什麼）需要的是**另一類來源**——建築技術規則、防火門 A/B 分級、採光通風規定這種法規，與畫法來源是兩回事，不能從製圖規範推導（資料自己的 `_meta.content_state` 已經這樣寫了，`SymbolRecord` 也把它型別成 `string | null`）。

把它留在清單裡，等於宣告「沒有法規注意事項的符號就不算查證完成」，那是把兩條軸混成一條——`CONTEXT.md` 對 `source_tier` 與 `verification_status` 警告過同一件事。

`verified_at` 與 `verified_by` **維持必填**。它們記錄「誰在什麼時候查的」，那正是查證這件事本身的一部分，M1 在翻牌時自然會填（13 筆目前也是 `null`）。

## Testing Decisions

**什麼是好的測試**：只測外部行為——使用者打開哪個網址、看到哪些字、按下按鈕之後圖上哪些熱區亮了。不測元件內部 state、不斷言函式回傳的物件形狀。

**三條 seam，其中兩條是既有的**：

**① 頁面層 / 真瀏覽器（既有，主要）** — `playwright.config.ts` 的 `webServer` 跑 `npm run build && npm run start`，測的是 SSG 產物本身，不是 dev server。所有新路由走這條。M2 的 67 條測試都在這裡，M3 沿用，不新增專案設定。

**② build 時資料驗證（既有）** — `tests/build-validation.spec.ts` 已經建立了「複製 `data/` 與 `scripts/` 到 tmp、改壞、跑 `validate_data.py`、斷言非零退出」的手法。三條新檢查各加一條測試，沿用同一個 sandbox，**不得改動 repo 裡的真資料**。

**② 的延伸（2026-09-13 決議）** — 同一套 sandbox 手法另外用來跑一次 `tsc`，只為了票 05 那一條驗收條件：「文案常數少一個分類的中文名時，`npm run typecheck` 失敗」。那道保證住在 `CATEGORY_LABELS` 的型別註記上，不真的跑一次 tsc 就驗不到。它把 `app/`、`components/`、`lib/` 與 `tsconfig.json` 複製到 tmp、symlink `node_modules`、自己寫一份最小的 `next-env.d.ts`，約 3–4 秒。手法與 ② 相同（複製到 tmp、改壞、跑檢查、斷言非零退出），跑的檢查不同——寫在這裡，免得下一次 review 把它當成沒人同意過的第四條 seam。

**③ 搜尋比對的純函式（新，唯一的新 seam）** — 跑在 Playwright 的 node context，不需要 `page` fixture，**不新增測試框架、不改 config**。

第三條是對 M2「不另外替純模組開單元測試」那條規矩的**刻意破例**。M2 立那條規矩的理由很具體：已知的 bug 都躲在 client px → 圖面 cm 的換算層，只測純模組會把最會壞的地方留在測試外。這個理由在搜尋上不成立——比對邏輯與版面尺寸完全無關，而它的風險是**組合性的**（46 個 aliases × 大小寫 × 全形半形 × 空白），瀏覽器測試只能抽樣，抽不到的那一組就是會出事的那一組。

**必須涵蓋的案例**：

1. `/` 不是 404，且有一個連往 `/layouts/3b2l_standard` 的入口
2. 14 個 symbol id 各自有一張 `/symbols/[id]`，都回 200
3. 符號頁的標題不等於根版面的標題，且 14 頁彼此不同
4. 符號頁的字全部來自資料：測試自己讀 `data/symbols.sample.json`，斷言頁面上出現的是**資料裡那一字不差的字串**。
   **不要用「改一筆資料看頁面跟不跟著變」來測**——那需要重跑 `next build`，不屬於三條 seam 任何一條（`build-validation` 的 sandbox 不跑 `next build`：它跑的是 `validate_data.py`，以及 ② 的延伸那一次 `tsc`）。測「渲染出來的等於資料裡的」已經足以證明沒有人把字寫死在元件裡，而且不必動到真資料
5. `caution` 為 `null` 的符號（13/14），頁面上沒有「注意事項」這個標題
6. 雨遮的頁面**有**注意事項
7. 符號頁印得出 `source_refs` 的每一筆；`cns` 的四筆看得到 `via` 那一行
8. `verification_status` 的四個值**都不出現**在任何一頁的 HTML 裡
9. 分類頁剛好 3 張；`plumbing_electric` 與 `fire_safety` 不產生頁面
10. 每張分類頁列出的符號數與資料一致
11. 搜尋打「灑水頭」這類 alias 找得到對應符號（純函式 seam）
12. 搜尋對大小寫、全形半形、前後空白不敏感（純函式 seam）
13. 首頁的搜尋框打字之後結果當場變動，不需要換頁
14. 點窗的符號頁按鈕 → 到 `/layouts/3b2l_standard?symbol=window` → 圖上 9 個窗熱區同時是 `highlighted`
15. 高亮狀態下縮放與拖曳照常運作
16. 高亮狀態下點圖上圈得出候選的地方 → 高亮清掉、開始新的第一段（**不是**直接跳出說明卡）；點到空白處、雙擊放大 → 高亮留著（2026-09-13 決議 D1）。落地時狀態列說出處數（D2）；`?symbol=` 對不到符號時提示找不到、不照印網址裡的字（D4）
17. 樑的按鈕文案是「看不到」那一句；點進去之後圖上出現橫幅，且**沒有**說明卡
18. 免責聲明出現在首頁、分類頁、符號頁、平面圖頁
19. sitemap 列出全部 **19** 個網址：1 首頁 + 14 符號頁 + 3 分類頁 + **`/layouts/3b2l_standard`**（產品本體、轉換點的落地處，PRD §8 的 IA 也列了它）
20. 三條新的建置檢查各自擋得住對應的壞資料
21. **把一個 `caution` 為 `null` 的符號翻成 `verified`（並填上 `verified_at` / `verified_by`），資料驗證仍然通過、build 仍然成立**——這條是在守住 M1 與 M3 的並行，它壞掉的時候壞的不是一個頁面而是整條建置線
22. `verified_at` 或 `verified_by` 為空卻標 `verified` 時，建置**仍然失敗**——移除 `caution` 不是把這條檢查整個放掉

## Out of Scope

- **找找看小遊戲與學習進度**（M4）。M3 只提供搜尋索引的純函式讓 M4 復用，不出題、不計分、不接 `fitLocked` 的 UI
- **Analytics 埋點**（M5）。§9.1 的 `symbol_view` 事件（含 `source: "search" | "category"`）不在 M3
- **Lighthouse 與 SEO 稽核**（M5）。M3 產出每頁的標題、描述與 sitemap；跑工具、修分數是 M5
- **第 2、3 張格局範例圖**（M6，而且是「上線後依數據**決定**要不要畫」）。M3 的紀律只有「不得寫死 `3b2l_standard`」
- **M1 的內容查證**。與 M3 並行：9 個 `convention` 補第 2 個交叉來源只會讓符號頁的來源清單多一行，不改變頁面形狀。查證率 80% 是 **M5 的上線門檻**，不是 M3 的前置。
  **但兩線不是完全不相干——有一個耦合點**：M1 一把符號翻成 `verified`，現行的 `REQUIRED_WHEN_VERIFIED` 就會因為 `caution` 為 `null` 而讓 build 斷掉，連帶弄掛 M3 的所有頁面測試。修法見上面的「要改的那一條」，**它必須排在 M3 最前面**。除此之外兩邊不碰同一個檔案（M1 動 `data/symbols.sample.json`，M3 動 `app/`、`lib/`、`components/`、`tests/`）
- **`co_occurs_with`**。PRD §7.2.1 降為選填、M1 結束後一次補齊，前台目前沒有用它的地方
- **`ai_description` / `detection_hints` 上前台**。它們是寫給模型看的（PRD §7.2.1），不是寫給讀者看的，階段二才有消費者
- **關於本站 / 免責聲明獨立頁**。PRD §8 的 IA 有這個節點，但 §6.4 要求的「每頁固定顯示」由頁尾滿足了，獨立頁沒有它自己的工作

## Further Notes

- **符號頁的內容量偏薄，這是已知的。** `plain_meaning` 每筆 40–60 字，而 14 筆裡只有雨遮有 `caution`。單頁的實質內容大約是：一句白話 + 1–2 則「容易搞混」+ 一筆出處。這對競爭型關鍵字不夠，但對長尾問句（「平面圖 深灰 淺灰 差別」）是真的答得上。**不要為了衝字數把 `ai_description` 搬上前台**——那是寫給模型的客觀幾何描述，讀起來不像人話，而且會弄壞 §7.2.1 建立的「客觀描述 vs 主觀判斷」那條界線。真正該補的是 `caution`，而它需要的是法規來源（建築技術規則、防火門分級、採光通風），與畫法來源是兩回事，屬於 M1 的後續。
- **`related_layouts` 的意思在 2026-09-12 定案**：它是「這個符號的頁面該把讀者帶去哪張圖」這個**編輯決定**，不是「這個符號出現在哪些圖上」的統計。所以樑填 `['3b2l_standard']` 是對的。PRD §7.2 的字面說法（「出現在哪些格局範例中」）與此不符，以 `CONTEXT.md` 為準。
- **轉載算 `verified` 也在同一天定案**（`CONTEXT.md`）。`docs/adr/0001` 已經把「核對 CNS 標準原文」從本專案的查證流程裡刪掉，所以 `via` 填齊就是那 4 個符號的流程終點。這與 PRD v0.6 改寫 M2 的 44px 驗收條件是同一類修正：一個後來的決定讓先前寫好的驗收條件在字面上不可能通過。
- **而 M1 的 80% 門檻有兩道閘門，Q6 只拆掉第一道。** 第一道是「轉載算不算 `verified`」（拆掉後上限從 10/14 = 71% 變成 14/14）；第二道是 `REQUIRED_WHEN_VERIFIED` 裡的 `caution`，它把上限壓到 **1/14 = 7%**，因為 14 筆裡只有雨遮有 `caution`。第二道在寫這份 spec 時才被發現，修法見「要改的那一條」。**教訓是同一個**：驗收條件是算術，寫下來之後要真的算一遍——M2 的 44px、Q6 的轉載、這裡的 `caution`，三次都是同一種病。
- **M1 有兩筆順手的資料修正**，不屬於 M3 但已經查出來了：（1）4 個 `cns` 符號的 `via` 都寫 `p32`，但表 14 的「引用 CNS11567」註記在 **p31**，p32 是「續」；（2）`source_refs` 目前 14 筆**沒有任何一筆有 `url`**，而符號頁的法規連結需要它。
- **repo 根目錄的 `平面圖符號.pdf` 就是《室內設計裝修製圖規範》本身**，也就是 13 個非雨遮符號現有那筆 `source_refs` 引的同一份文件。它**不能**當第 2 個交叉來源。它的前言（p2）點名了候選：《公共工程製圖手冊》（工程會）、《CNS 工程製圖》、《CNS 木工專業製圖》——但措辭是「參照」而非「引用」，p6 的「2. 引用標準」正式只列 `CNS11567，A1042，建築製圖` 一筆。
- **一張符號頁上的圖形必須與平面圖上畫的一致。** 這是本站的核心承諾（PRD §12），而 `docs/adr/0005` 之後主圖由 `FloorPlanRenderer` 畫、且它站 sprite 那一邊。符號頁直接用 sprite 就自動一致，**不要另外畫一套**。
- **`scripts/serve-static.mjs` 的 MIME 表只有 `.html` / `.js` / `.css` / `.txt`**，其餘一律 `application/octet-stream`。sitemap 是 `.xml`，要順手把它加進去——否則測試可能過了，而本機預覽時瀏覽器把 sitemap 當檔案下載。
- **「高亮是疊層而不是第四個 stage」值得在實作時寫成 ADR**：它難逆（建好之後要改就得動狀態機）、會讓未來的讀者問「為什麼高亮不是一個階段」、而且有一個具體被拒絕的替代方案（複用 `candidates`）。三個條件都滿足。**ADR 要寫對理由**：拒絕複用 `candidates` 不是因為命中判定會出錯（`tap()` 看 stage 分流，`browsing` 之下第二段永遠不會接管），而是因為檢視器的 `data-state` 不看 stage，會把它們畫成與真候選無法分辨的樣子——那是詞彙與視覺的問題。寫錯理由的 ADR 比沒有 ADR 更糟：下一個人會照著錯的理由去推翻它。
