# 04: pan/zoom 手勢

**What to build:** 使用者可以自己決定要細看圖的哪一區：雙指縮放、拖曳平移、雙擊快速放大、一鍵回到全圖。兩段式點擊解決的是「點得到」，pan/zoom 解決的是「看得清楚」，兩者都要有（PRD §6.1.1）。

**Blocked by:** 02（兩段式點擊選到符號）

02 已經把換算層建在 CSS transform 上，這張票加的是使用者發起的手勢，不重寫換算。

**Status:** done

- [x] pinch zoom（雙指縮放）
- [x] drag pan（拖曳平移）
- [x] double tap zoom（快速放大到該區域）—— **只在 browsing 成立**，見決議 1
- [x] reset view（一鍵回到全圖）
- [x] 縮放有上下限，使用者不會把圖縮成一點或放大到只剩一條線 —— 上下限相對 fit 定義，見決議 2
- [x] 手勢與兩段式點擊不互相誤觸：拖曳不應被判定成一次 tap

- [x] 平移與縮放在手機上維持順暢（優先 CSS transform，避免每幀重繪 SVG）

- [x] 測試涵蓋：放大後點擊仍選得到正確的熱區；`fitLocked` 擋得住使用者縮放卻擋不住自動放大

## Comments

**2026-09-08 — 實作完成。**`tests/pan-zoom.spec.ts` 八條，全套 38 條綠。

手勢辨識放在 `components/useViewerGestures.ts`（pointer 事件 → action），判定全部留在
`lib/viewer/interaction.ts`，換算全部留在 `lib/viewer/view.ts`。手勢層的記帳走 ref 不走 state：
每秒六十次的 pointermove 若每一次都 render，平移就跟不上手指。

### 決議 1：雙擊只在「上一下什麼都沒選到」時放大

兩段式的第一段**本身就會放大**，所以「雙擊放大這一區」唯一能多做一件事的時機，
正是第一段什麼都沒圈到的那一下。其他時候第二下的意思是**確認**，
那是全站的基礎操作，不能被手勢搶走（PRD §6.1.1）——放行的話，
凡是點在畫面中央附近的確認都會被偷走（第一段會把命中的東西移到畫面正中央，
所以「第二下離第一下很近」在那裡是常態而不是例外）。

**這個限制很窄，要說清楚窄在哪裡。** 票 02 量過：全圖下 46px 換算成圖面 161cm，
「房子裡已經沒有一個點是空的」。所以在全圖、在房子裡，雙擊永遠不會觸發——
使用者也不需要它，因為第一段已經替他放大到 3 倍了（user story 19 要的
「不必用兩根手指就能放大一區」在那裡由兩段式本身滿足）。雙擊補的是另外兩塊：
房子外的留白，以及**已經放大之後**——倍率愈高，46px 換算出的公分數愈小，空的地方愈多。

窄不等於藏起來。落空時的提示因此改成「這附近沒有可以點的東西，換個地方點點看，
**或連點兩下放大這一區**」：那正是雙擊唯一會成立的時刻，不在那裡講，就沒有地方講了。

**這條界線放在狀態機，不在手勢層。** 手勢層只認得出「兩下、很快、同一個地方」——
那是手指的事實；那兩下**代表**什麼要看 `stage` 與 `lastTap`，而它們在狀態機裡。
`lastTap` 為 null 就表示上一下已經被回應完了（有人按過重選、關過說明卡、按過回到全圖、
或框變了），這一下因此是新的第一段。用這個訊號取代了原本要在每個出口手動呼叫的
`forgetLastTap()`——那種要靠人記得配對的東西，M3、M4 新增一個出口就會安靜地壞掉。

### 決議 2：縮放上下限相對 fit，不是絕對倍率

下限＝「整張圖剛好放得下」，上限＝它的 8 倍。說明卡升起來時 fit 小於 1，
上下限跟著框走才講得通；相對定義還讓 `RESIZE` 的等比調整保持 zoom ÷ fit 不變——
撞在上限的視野在框變之後仍然剛好在上限，不會被夾掉一截。

8 倍：這張圖 1197cm 寬，8 倍下 1cm 畫成 2.3px，柱與相鄰窗那 3cm 的間距看得見；再放大只剩一條線。

### 決議 3：第一段不再把使用者縮小

`firstTap` 的自動放大改成 `max(現在的倍率, fit × 3)`，不再一律跳到 3。
使用者自己放到 4 倍時再跳回 3 倍，是把他剛調好的視野拿走——而自動放大的目的是看得清楚，
已經夠清楚了就不必動它。以 fit 為基準（而不是絕對 3）另外收掉一個角落：
說明卡開著時點下去也是「fit 的三倍」，卡片收起後 `RESIZE` 等比調回來，兩邊講的是同一件事。

### 決議 4：`fitLocked` 擋縮放**與平移**，不擋「回到全圖」

一開始只擋縮放，理由是「平移不改變倍率」。那個理由不成立：使用者只要點一下，
第一段就會給他 3 倍（那是機制本身，照設計不擋），接著他可以用那個倍率**把整張圖逛完**。
放大的權限已經發出去了，再放行平移等於把它變成無限期的。所以平移一併擋。

代價是零：候選一定落在第一段的容錯圈裡，放大之後仍然在畫面內（3 倍下離中心最多 138px，
可視區域半寬 171px），作答不需要平移。

「回到全圖」不擋——它是回到被鎖定的那個視野，不是繞過鎖定。

M2 沒有 UI 打開這個開關，入口是網址參數 `?fitLocked=1`。它是**公開網址上的一個面**，
不是只有測試看得到的東西；留著它的理由是驗收條件本身要求測得到
「擋得住縮放、擋不住自動 3×」，而 spec 的 Testing Decisions 只認頁面層的真瀏覽器測試。
M4 接上遊戲狀態時改派同一個 `SET_FIT_LOCKED`，狀態機不必回頭改，這個參數可以一起收掉。

### 修掉的兩個換算錯

兩個都是「拿一份東西配另一份時刻的東西」，跟這個檔案一路以來壞的方式一樣：

1. `clampView` 原本用 viewBox 的長寬比推可視範圍的高度。框的長寬比與 viewBox 一致時沒差，
   **說明卡把框壓扁之後就有差**——那一刻它同時擋住圖的下緣、又允許畫面滑出圖外。
   改成由框自己的高度換算。
2. 上面那一改讓 `clampView` 開始吃「框」，於是 `RESIZE` 裡 `clampView(s, ...)` 的 `s`
   變成了**舊框**：新倍率配舊框算出來的可視範圍偏小，視野被往裡推一小段，
   而框變回來時那一段不會自己還原。症狀就是說明卡開了又關，圖悄悄偏掉 2.8px。
   `docs/adr/0003` 留的那筆欠帳（「開卡片 → 關卡片要回得到原本的視野」）走的就是這條路徑，
   走一次就抓到了。

### `/code-review` 之後改的東西

兩軸各抓到一件真的：**雙擊在全圖時的房子裡根本不會觸發**（決議 1 原本的說法過度樂觀，
已改寫並補上提示文案），以及 **`fitLocked` 從平移漏出去**（決議 4，已一併擋住並補測試）。
另外照標準軸的意見：把雙擊的 stage 判斷從手勢層移回狀態機（判定不該住在手勢層）、
手勢層的 `lastTap` 更名 `lastContact`（與 `ViewerState.lastTap` 差一個單位，
而單位混用是這個 repo 壞過兩次的方式）、抽出 `zoomBy`、拿掉 `ViewerConfig.fitLocked`
（`SET_FIT_LOCKED` 之後它沒有人用，一個開關兩個入口只會分岔）、`zoomTo` 更名 `zoomView`。

**沒有照做的一件**：標準軸建議 `clampView` 改吃單一 `Projection`，讓 RESIZE 那個
「舊框配新倍率」的錯不可能寫得出來。它不會不可能——`clampView({ ...s, view: 新視野 })`
一樣寫得出來，錯法只是換個拼法。而 `clampView` 的工作正是「拿**還沒成為狀態**的視野
去夾」，把框與視野分成兩個參數是這件事的誠實形狀。
