# 06: 鍵盤與無障礙

**What to build:** 鍵盤使用者能看完整張圖。兩段式點擊升為全站基礎操作之後，它是**所有人看圖的唯一方式**——所以鍵盤必須有一條完整的平行路徑，否則這個網站對鍵盤使用者等於不存在。

鍵盤路徑**不走兩段式**：兩段式解的是手指精度問題，鍵盤沒有這個問題。

**Blocked by:** 03（說明卡 bottom sheet）— Enter 要開得出說明卡

**Status:** done

## Comments

**2026-09-10 實作完成。** 三件實作時才知道的事：

1. **「落在所有 room 之外」的只有 3 個雨遮，不是票上列的三類。** 票裡把「雨遮、外牆、外側的窗」
   一起當成房間之外的東西，但 `rooms[].geometry` 是**含牆厚**的外框，而外牆與外側的窗就畫在那條牆上——
   它們有一半落在房間的幾何裡。歸屬因此走「重疊面積最大者」，外牆與窗自然歸到它們所屬的房間
   （`hs-wall-exterior` → 主臥、`hs-win-living` → 客廳），只有整個掛在房子外面的雨遮走「最近的房間」。
   票上「排在該房間的最後」那條規則照舊，只是實際適用的對象少了兩類。

2. **走道一個熱區都沒有。** 開口與門都跨在兩間房中間、重疊面積剛好各半，這時取**面積小的那一間**——
   所有的門與開口因此歸到它們服務的那個空間（`hs-door-master` → 主臥、`hs-door-hall-living` → 客廳），
   走道分不到。這是刻意的：五扇門全部堆在走道那一段，使用者會連聽五次「一般單開門」而分不出是哪一間的門。

3. **平面圖的 `<svg>` 不再是 `role="img"`。** ARIA 裡 `img` 的子樹是裝飾性的，把 37 個可聚焦的熱區
   放在它底下等於宣告那些東西不存在。改成 `role="group"` + 原本那句 aria-label，圖面產物本身
   `aria-hidden`——它是一堆線，念出來只有「圖片」兩個字，而同一份內容讀得出來的那一版就是熱區層。
   既有測試用 `getByRole("img")` 當量尺寸的把手，一併改成 `getByRole("group")`。

**沒有一併做的事**：PRD §9 那段「v0.5 未決」還寫著「實作前必須先定」。決定已經落在
`.scratch/m2-viewer/spec.md` 與這張票，但 PRD 本文沒動——PRD 是產品規格、不是 build 單位（CLAUDE.md）。

**2026-09-10 code review 後的修正**（`/code-review` 兩軸各跑一次）：

- **鍵盤開過卡片、之後改用手指點圖時，卡片會把焦點搶走**（Spec 軸抓到）。「從哪個熱區來的」
  只在按下關閉鍵時清掉，而「看完一張卡直接點圖上別處」那條路不經過關閉鍵（PRD §11 #20），
  記錄就留了下來。改成手指一碰到圖就清掉，並補一條走那條路的回歸測試（先確認它在修好之前是紅的）。
- **房間歸屬本身沒有測試護欄**（Spec 軸抓到）。原本的順序測試讀的是頁面自己宣稱的 `data-room`，
  歸屬算錯了照樣全綠。補一條「熱區歸到圖上實際所在的那一間房」的定錨測試，用人看得懂的事實逐筆對，
  挑的是會分岔的那幾個（跨房的門、畫在牆上的窗、掛在外面的雨遮）。
- **`FOCUS_HOTSPOT` 沒有被 `fitLocked` 擋**（Spec 軸提出）。裁定**維持不擋**，理由與它不擋
  `firstTap` 自動放大相同，已寫進 `spec.md` 的「為 M4 預留的介面」與程式註解。
- Standards 軸的四則：`hasSymbol` / `rectOf` / `PlanRect` 收成共用（`lib/floorplan/hotspots.ts`）、
  第二段與 Enter 共用 `confirmSelection`、`takeFocus` 不再於 render 期讀 ref。
